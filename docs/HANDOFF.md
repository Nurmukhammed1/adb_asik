# CineMatch: передача работы

Этот текст — для модели, которая продолжит проект. Здесь: что это за проект, что уже сделано и проверено,
в каком состоянии машина, что осталось и как это делать.

## 1. Что это за проект

Учебный проект по курсу Advanced Databases: два задания, второе продолжает первое.

- **Assignment #6** — слой данных и бэкенд рекомендательной платформы на NoSQL: модель данных, регистрация
  и профили, каталог, история действий, поиск, API, тестовые данные. Сдаётся: proposal (с разделом
  «Relevance to the dissertation», 0.5–1 стр.), работающий бэкенд, документация API, инструкция по запуску,
  отчёт (номер и название, цели, скриншоты хода работы, источники).
- **Final Project** — рекомендации на коллаборативной фильтрации, API рекомендаций, пользовательский
  интерфейс, **тесты производительности при росте базы**, **оптимизация (индексы, кэш)**. Сдаётся: работающее
  приложение, инструкция по запуску, отчёт по производительности и оптимизации, презентация, итоговый отчёт
  (название, цели, скриншоты, таблицы и графики производительности, источники).

Тема — стриминг фильмов «CineMatch» на данных MovieLens. Тема диссертации пользователя не подошла, поэтому
взята общая тема; по заданию её должен одобрить преподаватель.

**Пользователь** пишет по-русски, отвечать по-русски. Интерфейс, код, комментарии и документация проекта —
на английском.

## 3. Что сделано и проверено

  проверялся** (окно браузера было скрыто, скриншоты не делались).
- **Docker:** `docker compose --profile app up -d --build` поднимает базу, API (5196) и сайт (8080). Проверено.
- **Документация API:** Scalar на `/scalar/v1`, `docs/openapi.json`, Postman-коллекция из 31 запроса.

- **Инструмент замеров** `tools/CineMatch.Perf` написан и отработал на наборе small (без индексов и с ними).

## 5. Что осталось и как это делать

### 5.1. Замеры на больших данных (требование 6 Final Project)

Нужна таблица «время ответа при росте базы» для small / 1m / 10m / 32m, до и после оптимизаций.

Порядок для каждого набора (API должен быть запущен, лучше из исходников в Release:
`dotnet run -c Release --project backend/src/CineMatch.Api --launch-profile http`; перед этим остановить
контейнер api, он занимает порт 5196):

```
P="dotnet run -c Release --project backend/tools/CineMatch.Perf --"
$P prepare --dataset 1m          # СТИРАЕТ базу, грузит набор, строит таблицу сходства
$P indexes drop
$P run --stage no-indexes --iterations 20 --max-seconds 20
$P indexes create
$P run --stage indexes
```

Важно:
- **Замер без индексов очень медленный** — каждый запрос к оценкам читает всю коллекцию. На 1M это до 5–6
  минут при настройках по умолчанию, на 10M и 32M — намного дольше, поэтому там обязательно уменьшать
  `--iterations` и `--max-seconds`. Текстовый поиск без индекса не работает вообще — это ожидаемо и в
  сводке помечается как «failed».
- **Не прятать вывод** длинных команд за `tail`/`grep` и заранее говорить пользователю, сколько это займёт.
  Он уже один раз прервал прогон, потому что тот выглядел зависшим.
- **`prepare` стирает базу** вместе с аккаунтом пользователя. Перед запуском спросить.
- Наборы 10m (архив ~63 МБ) и 32m (~239 МБ) ещё не скачивались и не импортировались — это первая проверка
  импортёра и построения сходства на таком объёме. На 32M матрица оценок займёт около 1–1.5 ГБ памяти.
- После каждого `run` сводка `perf/results/summary.md` и CSV пересобираются сами.
- В конце вернуть базу в удобное для показа состояние (например small — там есть номера TMDB) и
  пересоздать индексы.

### 5.2. Кэш Redis (требование 7 Final Project)

Не начато. В `docker-compose.yml` Redis уже есть, в `appsettings.json` есть `Redis:ConnectionString`.

План:
1. Пакет `StackExchange.Redis` в `CineMatch.Infrastructure`. Интерфейс кэша в `CineMatch.Core`
   (получить / записать с временем жизни / удалить), реализация на Redis в Infrastructure.
2. Кэшировать в `RecommendationService`: личные рекомендации (ключ по пользователю и лимиту, жизнь ~30
   минут) и популярные списки по жанрам (~10 минут).
3. Сбрасывать кэш пользователя при добавлении и удалении его оценки и при изменении любимых жанров; после
   пересчёта таблицы сходства сбрасывать всё (проще всего — номер версии в ключе).
4. Если Redis недоступен, запрос должен отработать без кэша, а не упасть.
5. Тесты: попадание в кэш, сброс после оценки, работа без Redis.
6. Замерить новый этап (`run --stage redis-cache`) и сравнить с `indexes`. Учесть, что инструмент шлёт
   повторные запросы за одних и тех же пользователей, так что эффект кэша будет виден сразу.

## 6. Как проверять

```
docker compose up -d                                   # база
dotnet test backend                                    # 81 тест, Docker должен работать
npm --prefix frontend test                             # 28 тестов
dotnet run --project backend/src/CineMatch.Api --launch-profile http   # API из исходников
npm --prefix frontend start                            # сайт на :4200, /api проксируется на :5196
```

Вход для проверки: создать аккаунт через сайт или API. Админа для проверки можно получить, выставив
`role: "admin"` своему тестовому аккаунту в коллекции `users`; после проверки тестовые данные убрать.
Оценки удалять через API, а не напрямую из базы — иначе разойдётся статистика фильмов.

## 7. Грабли, на которые уже наступали

- **Порт 5196** занят либо контейнером api, либо API из исходников — одновременно нельзя.
- **MongoDB 8:** `distinct` по массиву возвращает `undefined` для документов с пустым массивом.
- **.NET 10 OpenAPI:** если у метода есть `ProducesResponseType` для 400/404, ответ 200 надо объявлять явно.
- **CsvHelper 34** несовместим со старым API — в импортёре свой разборщик CSV, пакет удалён.
- **Angular 22:** `rxResource` принимает `params` и `stream`; `input()` разрешён только в классах с
  `@Component` или `@Directive`; обнаружение изменений без zone.js; иконки — Material Symbols.
- **Postman-коллекция и `docs/openapi.json`** при изменении API сами не обновляются. `openapi.json`
  выгружается с работающего API (`/openapi/v1.json`); скрипт-генератор коллекции в репозиторий не вошёл,
  коллекцию править вручную.
- **Git Bash на Windows:** многострочные heredoc-скрипты иногда ломаются на кавычках; длинные правки файлов
  надёжнее делать инструментом редактирования.
